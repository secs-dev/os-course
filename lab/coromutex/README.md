# Coroed Mutex

> [!NOTE]
> Формулировка данного задания является результатом работы ChatGPT, направленного на соответствующую задачу курса Романа Липовского.

## Постановка задачи

Вам дан [Coroed](https://github.com/vityaman-edu/coroed) — простой фреймворк для конкурентного исполнения stackful-корутин на пуле потоков.

В этой работе вам предстоит реализовать эффективный примитив синхронизации корутин — серийный неблокирующий кластеризующий мьютекс (serial lock-free combining mutex).

### Проблема

Для защиты разделяемых данных при конкурентном исполнении корутин требуется взаимное исключение.

Обычный `pthread_mutex` блокирует поток операционной системы при конкуренции за мьютекс. Если поток исполняет корутины, его блокировка останавливает не только ожидающую корутину, но и все остальные корутины, которые могли бы исполняться на этом потоке.

Мьютекс для корутин должен приостановить только текущую корутину, передав поток другой работе.

Однако даже такой мьютекс может работать неэффективно при высокой конкуренции. Каждый переход владения сопровождается операциями синхронизации, изменением состояния планировщика и переключением контекста. Кроме того, передача критической секции между процессорными ядрами ухудшает локальность данных в кэше.

### Идея

Реализуйте мьютекс, который при высокой конкуренции объединяет ожидающие критические секции в последовательность и исполняет их серийно, минимизируя обращения к планировщику, переключения между потоками и атомарные операции.

Вместо независимого пробуждения каждой ожидающей корутины мьютекс должен уметь непосредственно передавать исполнение следующей корутине (symmetric transfer).

В результате несколько критических секций могут исполняться подряд на одном рабочем потоке, сохраняя локальность защищаемых данных в процессорном кэше.

Цель: добиться того, чтобы увеличение конкуренции за мьютекс позволяло эффективнее амортизировать накладные расходы на синхронизацию, а не приводило к пропорциональному росту этих расходов.

## Требования к реализации

### 1. Mutex

Реализуйте примитив `Mutex` для корутин Coroed с операциями захвата и освобождения.

- Захват свободного мьютекса должен происходить без переключения контекста.
- При попытке захвата занятого мьютекса корутина должна приостанавливаться, не блокируя поток ОС.
- Критические секции должны исполняться со взаимным исключением, в том числе на разных рабочих потоках.
- Реализация должна исключать потерянные пробуждения (lost wakeups) и повторное планирование одной корутины.

Интерфейс должен быть привычным для пользователя: синхронизация не должна требовать явного взаимодействия с планировщиком.

### 2. Lock-free

Реализуйте синхронизацию внутри мьютекса без использования `pthread_mutex`, спинлоков или других блокировок.

Для координации конкурирующих потоков используйте атомарные операции и неблокирующие структуры данных.

Обратите внимание: lock-free здесь относится к внутреннему алгоритму управления состоянием мьютекса и очередью ожидания. Сам захват занятого мьютекса по определению требует ожидания освобождения критической секции.

### 3. Combining / Symmetric Transfer

Реализуйте серийное исполнение критических секций.

При освобождении мьютекса корутина должна иметь возможность непосредственно передать управление следующей ожидающей корутине, минуя обычный цикл планирования задач.

Добейтесь следующих свойств:

- Несколько конкурирующих критических секций могут исполняться последовательно на одном потоке ОС.
- Передача владения между ожидающими корутинами не требует повторного захвата свободного мьютекса через общую атомарную переменную.
- При наличии очереди ожидающих корутин не требуется возвращаться в планировщик между каждой парой критических секций.
- Механизм должен корректно взаимодействовать с вытесняющим планированием Coroed.
- Длительная конкуренция не должна приводить к бесконечному голоданию отдельных корутин.

Продумайте, когда следует завершать кластер последовательных критических секций и возвращать управление обычному планировщику.

### 4. Эффективность

Оптимизируйте накладные расходы на синхронизацию:

- Избегайте динамических аллокаций на пути захвата и освобождения мьютекса.
- Минимизируйте количество атомарных операций при высокой конкуренции.
- Используйте максимально слабые корректные `memory_order`.
- Не допускайте активного ожидания мьютекса корутинами.
- Изолируйте детали синхронизации от внутренней реализации планировщика.

Для хранения ожидающих корутин рассмотрите интрузивную очередь.

## Тестирование

Разработайте тесты, проверяющие взаимное исключение, отсутствие потерянных пробуждений и корректность передачи владения при конкурентном исполнении большого количества корутин.

Особое внимание уделите одновременной постановке корутин в очередь, освобождению мьютекса и вытеснению корутин планировщиком.

## Benchmark

Реализуйте простой мьютекс для корутин, который при освобождении передаёт ожидающую корутину обычному планировщику.

Сравните его с кластеризующей реализацией при различном количестве рабочих потоков, конкурирующих корутин и длительности критических секций.

Измерьте:

- Пропускную способность — количество исполненных критических секций в секунду.
- Количество атомарных операций на критическую секцию.
- Количество переключений контекста.
- Задержку ожидания захвата мьютекса.

Объясните полученные результаты. При каких условиях кластеризация даёт преимущество? Когда она становится неэффективной? Как размер кластера влияет на справедливость планирования?
