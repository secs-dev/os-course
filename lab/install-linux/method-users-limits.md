# Методика. Пользователи и ограничение ресурсов

Общая инструкция по управлению пользователями в Linux и настройке ограничений
(sudo, дисковые квоты, лимиты процессов). Не привязана к конкретной лабораторной
работе — конкретные логины, значения квот и лимитов задаются в задании.

## 1. Создание и управление пользователями

```bash
# создать пользователя с домашним каталогом и указанным shell
sudo useradd -m -s /bin/bash guest

# то же самое, но в интерактивном/дружелюбном виде (задаст вопросы, установит пароль)
sudo adduser guest

# установить/сменить пароль
sudo passwd guest

# добавить пользователя в дополнительную группу (например sudo)
sudo usermod -aG sudo guest
# на Arch группа для полного sudo-доступа обычно называется wheel:
# sudo usermod -aG wheel guest

# посмотреть, в каких группах состоит пользователь
groups guest
id guest

# удалить пользователя вместе с домашним каталогом
sudo userdel -r guest
```

Домашний каталог по умолчанию создаётся в `/home/<логин>` из шаблона
`/etc/skel`. Если каталог нужно создать отдельно или в нестандартном месте:

```bash
sudo mkdir -p /home/guest
sudo chown guest:guest /home/guest
sudo chmod 750 /home/guest
```

## 2. Настройка sudo с ограниченным набором команд

Полное включение в группу `sudo` даёт пользователю root-доступ ко **всем**
командам. Чтобы выдать доступ только к конкретным командам, используется
отдельный файл в `/etc/sudoers.d/`:

```bash
sudo visudo -f /etc/sudoers.d/guest
```

Содержимое файла (пример — разрешить только перезапуск одной службы и просмотр
логов, без пароля):

```
guest ALL=(root) NOPASSWD: /usr/bin/systemctl restart myservice, /usr/bin/journalctl -u myservice
```

Важно: редактировать файлы sudoers **только через `visudo`** (или `visudo -f`) —
он проверяет синтаксис перед сохранением и не даст сохранить файл, который
сломает sudo для всех пользователей.

Проверить, что именно разрешено пользователю:

```bash
sudo -l -U guest
```

## 3. Дисковые квоты

Квоты ограничивают объём данных (и/или число файлов — inode), которые
пользователь может хранить в файловой системе.

### 3.1 Подготовка

1. Установить утилиты:
   ```bash
   sudo apt install -y quota
   # на Arch пакет называется иначе, но даёт те же утилиты:
   # sudo pacman -S quota-tools
   ```
2. Включить поддержку квот для нужной файловой системы в `/etc/fstab`, добавив
   опции `usrquota` (и/или `grpquota`) к строке монтирования:
   ```
   UUID=xxxxxxxx-....   /home   ext4   defaults,usrquota   0   2
   ```
3. Перемонтировать и инициализировать файлы квот:
   ```bash
   sudo mount -o remount /home
   sudo quotacheck -cum /home
   sudo quotaon /home
   ```

   Поддержка квот и синтаксис их включения немного различаются между
   файловыми системами (ext4, XFS используют разные механизмы — например, у XFS
   квоты включаются опцией монтирования `uquota`/`pquota`, а не через `quotacheck`).
   Проверяйте документацию конкретной ФС, если используете не ext4.

### 3.2 Установка квоты пользователю

Мягкий лимит (soft, предупреждение) и жёсткий лимит (hard, запись блокируется):

```bash
sudo setquota -u guest 90M 100M 0 0 /home
# soft=90M, hard=100M на объём данных; лимиты по числу inode не заданы (0 0)
```

Интерактивное редактирование:

```bash
sudo edquota -u guest
```

### 3.3 Проверка

```bash
quota -u guest
sudo repquota /home
```

### 3.4 Проверка срабатывания

От имени ограниченного пользователя попробовать записать файл больше квоты:

```bash
dd if=/dev/zero of=~/bigfile bs=1M count=200
```

При превышении жёсткого лимита команда завершится ошибкой вида
`dd: error writing '...': Disk quota exceeded`.

## 4. Ограничение числа процессов и других ресурсов

### 4.1 `ulimit` (в рамках текущей сессии)

```bash
ulimit -u          # текущий лимит числа процессов пользователя
ulimit -u 30        # временно установить лимит на 30 (действует до конца сессии)
```

`ulimit` меняет лимит только для текущего shell и его потомков — для
постоянной настройки нужен один из механизмов ниже.

### 4.2 `/etc/security/limits.conf` (постоянно, для сессий через login/PAM)

```
# /etc/security/limits.conf
guest    hard    nproc    30
guest    soft    nproc    30
```

Эти лимиты применяются PAM-модулем `pam_limits` при входе пользователя (через
`login`, `sshd`, `su -l` и т.п.). Если пользователь заходит в систему через
systemd user session/services, PAM-лимиты могут не применяться — тогда нужен
подход через systemd (см. 4.3).

Проверка после нового входа в систему под этим пользователем:

```bash
ulimit -u
```

### 4.3 Ограничения через systemd (более надёжный современный способ)

Для пользовательских systemd slice:

```bash
sudo systemctl set-property user-$(id -u guest).slice TasksMax=30
```

Или через `/etc/systemd/logind.conf`:

```
UserTasksMax=30
```

(изменение вступает в силу после перезапуска `systemd-logind` или перезагрузки).

### 4.4 Проверка лимита форк-бомбой (безопасно, под ограниченным пользователем)

> **Предупреждение.** Запускайте форк-бомбу **только** под пользователем, для
> которого уже настроен и проверен лимит числа процессов (`nproc`/`TasksMax`), и
> **никогда** под root или без предварительно настроенного лимита — иначе можно
> подвесить всю систему, а не только тестируемого пользователя.

Классическая форк-бомба (bash):

```bash
:(){ :|:& };:
```

Ожидаемый результат при корректно настроенном лимите: число процессов
пользователя перестаёт расти на уровне лимита, появляются ошибки вида
`fork: retry: Resource temporarily unavailable` — сама ВМ при этом остаётся
отзывчивой для других пользователей и процессов.

Остановить зависшие процессы после теста:

```bash
sudo pkill -u guest
```

## 5. Возврат системы в исходное состояние после тестов

После проверки ограничений стоит явно почистить артефакты тестирования:

```bash
# остановить оставшиеся процессы тестового пользователя
sudo pkill -u guest

# удалить тестовые файлы, созданные при проверке квоты
sudo rm -f /home/guest/bigfile

# проверить, что использование диска и число процессов вернулись к норме
quota -u guest
ps -u guest
```

Сами настройки ограничений (sudoers-файл, квота, лимит процессов) обычно **не**
нужно откатывать — они и есть результат работы, который должен остаться
настроенным.

## 6. Типичные проблемы

| Симптом | Причина | Решение |
|---|---|---|
| Квота не срабатывает | Не включена поддержка квот в `/etc/fstab` / не выполнен `quotacheck` + `quotaon` | Повторить шаги раздела 3.1 |
| `ulimit -u` показывает старое значение после правки `limits.conf` | Лимит из `limits.conf` применяется только при новом входе в систему | Полностью перелогиниться (новая SSH-сессия), а не просто открыть новый терминал в старой сессии |
| Пользователь всё равно может выполнить произвольную sudo-команду | В `sudoers.d` использован слишком широкий шаблон, либо пользователь состоит в группе `sudo`/`wheel` напрямую | Проверить `sudo -l -U <user>`, убрать пользователя из широких групп |
| Форк-бомба подвесила всю систему, а не только пользователя | Лимит `nproc`/`TasksMax` не был настроен или не применился до теста | Настроить и проверить лимит **до** запуска форк-бомбы; перезапустить ВМ, если она уже подвисла |
