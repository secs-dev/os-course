# Вводное задание: измерение производительности файлового ввода-вывода в Linux

> Экспериментальное введение в курс «Операционные системы». Задание учит ставить
> эксперимент над ОС корректно: фиксировать окружение, выбирать инструменты,
> планировать число измерений и обрабатывать результат статистически — а не
> делать вывод по 1–3 запускам «на глаз».

## 0. Цель работы

Сравнить время выполнения одной и той же задачи (чтение большого файла) при
разных стратегиях доступа к данным:

1. последовательное чтение через `read()`;
2. случайное чтение через `lseek()+read()`;
3. то же самое, но через отображение файла в память (`mmap`).

Итоговая метрика в каждой конфигурации — **одно число** (время выполнения),
полученное как статистически обоснованная оценка по серии измерений, а не
единичный запуск.

По итогу вы должны уметь: снять «паспорт» системы, подготовить окружение так,
чтобы измерения были воспроизводимы, спланировать серию экспериментов, честно
посчитать доверительный интервал и сделать вывод, которому можно доверять.

## 1. Что выдаётся

- `seq_rand_read` — программа, читающая файл заданного размера в одном из двух
  режимов: `seq` (последовательный `read()`), `rand` (случайный
  `lseek()+read()`, псевдослучайная последовательность смещений — **не**
  `/dev/random`, чтобы не создавать паразитный IO).
- `mmap_read` — аналогичная программа, но использующая `mmap()` вместо
  `read()`, с теми же двумя режимами доступа (последовательный обход
  отображённой памяти / случайный обход).
- Данный документ и вспомогательные методички в `docs/`.

Исходный код примеров и точные CLI-флаги программ — см. README рядом с
исходниками (`--mode`, `--size`, `--seed`, `--block-size` и т.п. — уточняйте по
`--help` конкретной сборки, которая лежит в репозитории).

## 2. Предварительные требования к стенду

- Linux (bare-metal или ВМ **с закреплёнными** vCPU; избегайте
  «burstable»/shared-core облачных инстансов — там шумные соседи ломают
  измерения сильнее, чем что-либо ещё).
- `gcc`/`make`, `perf`, `sysstat` (`vmstat`, `mpstat`, `pidstat`, `iostat`),
  `stress-ng`, `smartmontools`, `lshw`, `util-linux` (`taskset`), `time`
  (пакетная утилита `/usr/bin/time`, не bash-builtin).
- Права `sudo` понадобятся для: `drop_caches`, изменения governor CPU,
  отрицательного `nice`, иногда для `smartctl`.
- Задание платформо-независимо по духу: инструкция ориентирована на Linux, но
  идея эксперимента (сравнение seq/rand и read/mmap с контролем окружения)
  переносима на любую ОС — если у вас нет Linux, обсудите замену утилит с
  преподавателем **до** защиты.

## Этап 1. Исследование `seq_rand_read` (по инструкции)

### Шаг 1.1. Снять паспорт системы

Прежде чем что-то измерять, зафиксируйте, *на чём* вы измеряете — это
понадобится и для отчёта, и для того, чтобы объяснить неожиданные результаты.

```bash
uname -a
lscpu
lscpu -e                     # топология: сокеты/ядра/потоки, какие CPU — P/E-ядра
free -h
nproc
sudo lshw -class disk -class memory -short
sudo smartctl -a /dev/sdX    # модель, тип (SSD/HDD), состояние, TRIM
cat /sys/block/sdX/queue/rotational   # 0 = SSD/NVMe, 1 = HDD
```

Зафиксируйте также состояние «фона» перед началом:

```bash
uptime            # load average
top -bn1 | head -20
```

Подробнее, зачем каждая из этих команд и что с их выводом делать — см.
[`docs/monitoring.md`](docs/monitoring.md).

### Шаг 1.2. Подготовить окружение

Цель — убрать посторонние источники дисперсии: миграции между ядрами,
конкуренцию за CPU с другими процессами, DVFS (изменение частоты «на лету»),
непредсказуемое состояние файлового кэша.

Минимальный чек-лист (подробности и обоснование каждого пункта —
[`docs/environment.md`](docs/environment.md)):

```bash
# 1. Закрыть лишнее: браузер, IDE, фоновые синхронизации и т.п.
#    Цель — idle %CPU в top близко к 0 на всех ядрах.

# 2. Зафиксировать governor CPU (убрать переменную частоту)
sudo cpupower frequency-set -g performance
cpupower frequency-info      # проверить, что governor применился

# 3. Выбрать конкретное ядро под эксперимент и закрепить процесс на нём
taskset -c 2 ./seq_rand_read --mode seq --file testfile.bin

# 4. При необходимости поднять приоритет, чтобы планировщик не откладывал процесс
sudo nice -n -5 taskset -c 2 ./seq_rand_read ...
# renice — для уже запущенного процесса:
renice -n -5 -p <pid>
```

Держите под рукой команду сброса файлового кэша — она понадобится в шаге 1.5
при выборе методологии «холодного» кэша:

```bash
sync; echo 3 | sudo tee /proc/sys/vm/drop_caches
```

### Шаг 1.3. Ознакомительные (baseline) измерения

Запустите программу по разу в каждом режиме и посмотрите на неё «изнутри» —
это не финальные измерения, а разведка.

```bash
/usr/bin/time -v taskset -c 2 ./seq_rand_read --mode seq  --file testfile.bin
/usr/bin/time -v taskset -c 2 ./seq_rand_read --mode rand --file testfile.bin
```

`/usr/bin/time -v` уже даёт: wall time, user/kernel time, maximum RSS, number
of voluntary/involuntary context switches, page faults (major/minor).

Дополнительно снимите более детальные счётчики через `perf stat`:

```bash
perf stat -e task-clock,context-switches,cpu-migrations,page-faults,\
cache-references,cache-misses \
  taskset -c 2 ./seq_rand_read --mode rand --file testfile.bin
```

И в соседнем терминале, пока идёт запуск — общесистемную картину:

```bash
vmstat 1
mpstat -P ALL 1
pidstat -urd 1
```

Затем повторите ознакомительный запуск **с фоновой нагрузкой**, чтобы увидеть,
как выглядит «шум» и почему его нужно убирать или контролировать:

```bash
stress-ng --cpu 2 --io 1 --vm 1 --vm-bytes 256M --timeout 30s &
taskset -c 2 ./seq_rand_read --mode rand --file testfile.bin
```

Обратите внимание на рост `cpu-migrations`, `involuntary context switches` и
разброс wall time — это именно то, что мы будем в дальнейшем подавлять или, по
крайней мере, держать под контролем.

Список всех метрик, которые стоит здесь снять, и как их читать — таблица в
разделе 5 этого файла и [`docs/monitoring.md`](docs/monitoring.md).

### Шаг 1.4. Сформулировать гипотезу

Прежде чем ставить серию измерений, явно запишите, что вы ожидаете увидеть, и
почему. Пример рассуждения (не единственно верный — обоснуйте свой вариант):

- Последовательное чтение использует OS readahead и меньше системных вызовов
  на байт — ожидаем **меньшее** время, чем случайное.
- На HDD случайный доступ обычно на порядки медленнее из-за времени
  позиционирования головки; на SSD/NVMe разница меньше, но всё ещё заметна
  из-за меньшей эффективности readahead и большего числа syscall'ов на тот же
  объём данных.
- Если размер файла заметно меньше объёма RAM и кэш не сбрасывается между
  запусками, после прогрева разница между seq и rand может **исчезнуть** —
  вы будете измерять скорость `memcpy` из page cache, а не диска. Это важно
  учесть в планировании (шаг 1.5): если цель — увидеть разницу дисковых
  паттернов доступа, размер файла должен заметно превышать объём свободной
  RAM, либо кэш должен явно и одинаково сбрасываться перед каждым запуском.

Гипотеза не обязана быть верной — важно, чтобы она была сформулирована *до*
серии измерений, а не подгонялась под результат постфактум.

### Шаг 1.5. Спланировать эксперимент

Зафиксируйте письменно (это пойдёт в отчёт) следующие решения:

1. **Единственная метрика на запуск.** По условию задания результат серии —
   одно число. Берите wall time выполнения (например, из `/usr/bin/time -v`
   или собственного таймера внутри программы, если он предусмотрен) как
   основную метрику; остальные счётчики (context switches, page faults,
   %CPU) — вспомогательные, для объяснения результата, а не для замены
   основной метрики.
2. **Методология кэша**: холодный кэш (`drop_caches` перед *каждым* запуском)
   или тёплый кэш (кэш прогревается и не трогается всю серию). Выберите одну
   и придерживайтесь её во всей серии — смешивать нельзя, иначе разброс будет
   объяснён не режимом доступа, а состоянием кэша.
3. **Размер файла** относительно объёма RAM — исходя из решения п.2.
4. **Число повторов N** на конфигурацию и порядок запуска. Не запускайте
   сначала все `seq`, а потом все `rand` — интерливинг (`seq, rand, seq,
   rand, ...` или случайный порядок) защищает от систематического дрейфа
   (например, нагрева процессора, фоновых cron-задач, троттлинга).
5. **Прогревочные запуски**: сколько первых запусков отбрасывается (если
   отбрасываются) и почему — явное решение, а не тихое исключение неудобных
   точек.
6. **Разделение измерения и мониторинга.** Финальную серию замеряйте
   минимально инвазивным способом (например, только `/usr/bin/time` или
   встроенный таймер программы). `perf stat`/`vmstat` в режиме постоянного
   опроса добавляют накладные расходы — используйте их для характеризации
   (шаг 1.3), а не как источник основной метрики финальной серии.

Как обосновать число N и что такое «доверительный интервал» в этом контексте
— подробно в [`docs/statistics.md`](docs/statistics.md). Там же — как
поступать с выбросами и когда стоит остановиться и не гнаться за «ещё больше
измерений».

### Шаг 1.6. Зафиксировать окружение перед серией

Повторите шаг 1.1 непосредственно перед стартом финальной серии измерений
(«снимок до»): `uptime`, `top -bn1`, температура/троттлинг при наличии
доступа (`sensors`, `cat /sys/class/thermal/thermal_zone*/temp`). Это нужно,
чтобы на защите вы могли показать, что фон был действительно тихим, а не
предполагался таковым.

### Шаг 1.7. Провести серию измерений

Пример каркаса скрипта сбора (адаптируйте под точные флаги вашей сборки
программы):

```bash
#!/usr/bin/env bash
set -euo pipefail

FILE=testfile.bin
CORE=2
N=30
OUT=results_read.csv
echo "timestamp,mode,run_id,wall_time_s,user_time_s,sys_time_s,vol_ctx,invol_ctx,minflt,majflt" > "$OUT"

modes=(seq rand)
for i in $(seq 1 $N); do
  # интерливинг режимов, а не блоками
  for mode in "${modes[@]}"; do
    # если выбрана методология "холодного" кэша:
    sync; echo 3 | sudo tee /proc/sys/vm/drop_caches > /dev/null

    ts=$(date +%s)
    /usr/bin/time -v taskset -c $CORE ./seq_rand_read --mode "$mode" --file "$FILE" \
      2> /tmp/time_out.$$ 1> /tmp/prog_out.$$

    wall=$(grep "Elapsed (wall clock)" /tmp/time_out.$$ | awk -F': ' '{print $2}')
    user=$(grep "User time"   /tmp/time_out.$$ | awk '{print $4}')
    sys=$(grep  "System time" /tmp/time_out.$$ | awk '{print $4}')
    volc=$(grep "voluntary context switches" /tmp/time_out.$$ | head -1 | awk '{print $1}')
    invc=$(grep "involuntary context switches" /tmp/time_out.$$ | awk '{print $1}')
    minf=$(grep "Minor (reclaiming a frame) page faults" /tmp/time_out.$$ | awk '{print $NF}')
    majf=$(grep "Major (requiring I/O) page faults" /tmp/time_out.$$ | awk '{print $NF}')

    echo "$ts,$mode,$i,$wall,$user,$sys,$volc,$invc,$minf,$majf" >> "$OUT"
    rm -f /tmp/time_out.$$ /tmp/prog_out.$$
  done
done
```

Требования к скрипту сбора:

- сохраняет **сырые** данные каждого запуска (не только среднее);
- сохраняет достаточно метаданных, чтобы воспроизвести запуск (режим,
  CPU pinning, размер файла, seed для псевдослучайного доступа);
- скрипт целиком входит в сдаваемые материалы и должен воспроизводимо
  запускаться на защите.

### Шаг 1.8. Проанализировать измерения

Для каждой конфигурации (`seq`, `rand`) посчитайте:

- выборочное среднее и стандартное отклонение;
- доверительный интервал для среднего (способ построения и обоснование —
  [`docs/statistics.md`](docs/statistics.md));
- проверьте наличие выбросов и явно опишите, что с ними сделано (оставлены /
  исключены и почему).

Постройте простое сравнение: столбчатую диаграмму средних с усами
доверительного интервала для `seq` и `rand`. Поскольку по условию задания
измерение точечное (а не зависимость от параметра), развёрнутый график не
нужен — достаточно сравнения двух/четырёх точек с интервалами.

### Шаг 1.9. Сформулировать вывод

Ответьте явно на три вопроса (они и есть костяк вывода):

1. **Сравнение.** Что больше/меньше и насколько? Согласуется ли с гипотезой
   из шага 1.4? Если нет — почему, какой механизм ОС/железа это объясняет?
2. **Погрешность.** Устраивает ли вас ширина доверительного интервала для
   того вывода, который вы делаете? Если интервалы `seq` и `rand`
   пересекаются — можете ли вы вообще утверждать, что есть разница?
3. **Достаточность.** Помогут ли делу ещё N измерений? Оцените (хотя бы
   грубо), во сколько раз нужно увеличить N, чтобы вдвое сузить интервал, и
   стоит ли это того при уже полученной картине.

## Этап 2. Исследование `mmap_read` (самостоятельно)

Повторите шаги 1.1–1.9 для программы `mmap_read`, самостоятельно написав
скрипты сбора по аналогии с Этапом 1. Отличия, на которые стоит обратить
внимание:

- у `mmap` нет системного вызова на каждое чтение — данные попадают в память
  процесса через **page fault** (minor fault — страница уже в page cache,
  major fault — реально требуется IO). Это значит, что основной счётчик,
  объясняющий разницу seq/rand для `mmap`, — не `context-switches`, а
  `minor/major page faults`;
- для `mmap`-случая имеет смысл отдельно посмотреть на `madvise`-эффекты,
  если программа их использует (`MADV_SEQUENTIAL`/`MADV_RANDOM`) — уточните
  по исходнику `mmap_read`, реализовано ли это, и как это влияет на readahead
  ядра;
- ожидайте, что выводы **изменятся** по сравнению с Этапом 1 — в этом и
  ценность повторного исследования. Не подгоняйте методологию под то, чтобы
  получить «те же» выводы.

- Какие условия измерения оказались критичными, а чем можно было пренебречь?

## 5. Ключевые измеряемые величины

| Величина | Что показывает | Источник |
|---|---|---|
| Wall time | Итоговая метрика запуска | `/usr/bin/time -v`, `perf stat`, либо таймер внутри программы |
| User time / Kernel(sys) time | Доля времени в пространстве пользователя vs ядра | `/usr/bin/time -v`, `perf stat` |
| %CPU | Загрузка ядра(-ер) во время запуска | `pidstat`, `top`, `mpstat` |
| Context switches (voluntary/involuntary) | Как часто планировщик снимал процесс с CPU и почему | `/usr/bin/time -v`, `perf stat -e context-switches` |
| CPU migrations | Перескоки процесса между ядрами (шум, если pinning не работает) | `perf stat -e cpu-migrations` |
| Page faults (minor/major) | Обращения к памяти/диску через MMU; ключевая метрика для `mmap` | `/usr/bin/time -v`, `perf stat -e page-faults` |
| RAM (RSS, page cache) | Потребление памяти процессом и состояние файлового кэша | `/usr/bin/time -v` (Maximum resident set size), `free -h` |
| Disk IO (reads, latency) | Реальная активность диска во время запуска | `iostat -x 1`, `pidstat -d 1` |
| Характеристики CPU/памяти/диска | «Паспорт» стенда для отчёта и объяснения результатов | `lscpu`, `lshw`, `smartctl`, `free -h` |

Подробнее по каждому инструменту — [`docs/monitoring.md`](docs/monitoring.md).

## 6. Настройка и изоляция окружения — кратко

Полное руководство: [`docs/environment.md`](docs/environment.md). Кратко,
что обязательно, а что опционально:

- **Обязательно**: закрыть фоновые процессы, зафиксировать governor CPU
  (`performance`), закрепить процесс на конкретном ядре (`taskset`),
  явно выбрать и задокументировать методологию кэша.
- **Желательно**: приоритет через `nice`/`renice`, снятие «снимка» нагрузки
  системы до и после серии.
- **Продвинуто/опционально**: `isolcpus`/cgroups для полной изоляции ядра от
  планировщика ОС, отключение Turbo Boost, отключение SMT/Hyper-Threading —
  обсудите с преподавателем, если хотите пойти дальше базового уровня.

## 7. Статистика измерений — кратко

Полное руководство: [`docs/statistics.md`](docs/statistics.md). Кратко:

- Считайте выборочное среднее и доверительный интервал (не только среднее
  «в лоб»).
- Для малых N (< 30) используйте t-распределение, а не нормальное
  приближение, при построении ДИ.
- Явно решите вопрос выбросов и прогревочных запусков **до**, а не после
  того, как увидели результат.
- Оцените, устраивает ли вас ширина интервала, и сколько измерений
  потребовалось бы для её уменьшения — это часть обязательного вывода
  (шаг 1.9, п.3).

## 8. Требования к защите

Будьте готовы по требованию:

- показать и заново прогнать скрипты сбора измерений на любой доступной
  машине (не только на той, где собирали изначально);
- объяснить каждое решение по настройке окружения (зачем `taskset`, зачем
  выбрана именно эта методология кэша и т.д.);
- объяснить, как посчитан доверительный интервал, и что произойдёт с
  выводом, если N увеличить/уменьшить;
- обосновать выбор размера файла относительно объёма RAM.
