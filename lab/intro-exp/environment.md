# Настройка и изоляция окружения эксперимента

Цель всех действий ниже — одна: убрать (или хотя бы сделать управляемыми)
источники дисперсии, которые не связаны с исследуемым различием (`seq` vs
`rand`, `read` vs `mmap`), но влияют на wall time запуска.

## 1. Фоновые процессы

Перед серией измерений закройте всё лишнее: браузеры, IDE, синхронизации
облачных папок, обновления пакетов, индексаторы файлов (`updatedb`,
`tracker`, Spotlight-аналоги на Linux — `mlocate`/`plocate` cron).

Проверка «фон тихий»:

```bash
uptime                 # load average должен быть близок к 0 на простаивающей машине
top -bn1 | head -20    # %CPU процессов, kernel threads в норме почти не грузят CPU
```

Если это ВМ в облаке — учтите, что вы не контролируете соседей по хосту.
Для учебных целей это допустимо, но результат в отчёте нужно
интерпретировать с этой оговоркой; для более чистого эксперимента
предпочтителен bare-metal ноутбук/десктоп или выделенная ВМ.

## 2. Частота CPU (DVFS) и Turbo Boost

Современные CPU меняют частоту «на лету» в зависимости от нагрузки и
температуры — это прямой источник нестабильности между запусками.

```bash
cpupower frequency-info                  # посмотреть текущий governor и диапазон частот
sudo cpupower frequency-set -g performance   # зафиксировать максимальную частоту
```

Governor'ы (`man cpupower`): `performance` (фиксированно максимум —
рекомендуется для экспериментов), `powersave`, `ondemand`/`schedutil`
(динамические — источник шума, для замеров не годятся).

Turbo Boost (Intel) / Precision Boost (AMD) — опционально, но если хотите
убрать ещё один источник разброса между запусками:

```bash
# Intel, если используется intel_pstate:
cat /sys/devices/system/cpu/intel_pstate/no_turbo   # 0 = turbo включён
echo 1 | sudo tee /sys/devices/system/cpu/intel_pstate/no_turbo  # выключить
```

Это продвинутый шаг — если недоступен на вашем железе/правах, просто
явно укажите в отчёте, что Turbo Boost не контролировался, и учтите это
при интерпретации разброса.

## 3. Закрепление процесса на CPU (`taskset`)

Без явного закрепления планировщик Linux может перемещать процесс между
ядрами (`cpu-migrations` в `perf stat`), что портит сравнимость запусков
(разные ядра — разное состояние L1/L2 кэша, разная текущая частота и т.д.).

```bash
taskset -c 2 ./seq_rand_read --mode seq --file testfile.bin   # закрепить на ядро 2
taskset -cp 2 <pid>                                            # закрепить уже запущенный процесс
```

Выбирайте ядро, не являющееся ядром с наибольшей фоновой нагрузкой (обычно
CPU0 обслуживает больше прерываний) — проверьте `mpstat -P ALL 1` перед
выбором.

## 4. Приоритет планировщика (`nice`/`renice`)

`nice` влияет на то, как охотно планировщик уступает CPU процессу при
конкуренции. Для «тихого» стенда это не критично, но полезно как
дополнительная защита от вытеснения:

```bash
sudo nice -n -5 taskset -c 2 ./seq_rand_read ...   # отрицательный nice → выше приоритет, нужен root
renice -n -5 -p <pid>                              # изменить приоритет уже запущенного процесса
```

Диапазон nice: от `-20` (наивысший приоритет) до `19` (наинизший).
Отрицательные значения — только с правами root.

## 5. Состояние файлового кэша — самое важное решение

Это решение сильнее всего влияет на то, что именно вы измеряете, поэтому
примите его осознанно и одинаково для всей серии одной конфигурации.

**Холодный кэш** (cold cache): перед *каждым* запуском гарантированно
убираете страницы файла из page cache:

```bash
sync
echo 3 | sudo tee /proc/sys/vm/drop_caches
```

(`1` — очистить только pagecache, `2` — dentries/inodes, `3` — всё; для
данного эксперимента нужен именно `3`, либо как минимум `1`).

Такой режим измеряет «настоящую» стоимость обращения к диску — на нём
разница `seq` vs `rand` будет наиболее выраженной, особенно на HDD.

**Тёплый кэш** (warm cache): кэш прогревается один раз (одним холостым
проходом по файлу) и далее не трогается всю серию. Такой режим измеряет,
по сути, эффективность доступа к уже закэшированным данным в памяти — разница
`seq` vs `rand` для `read()`-варианта здесь может быть минимальной, а для
`mmap` всё ещё может проявляться через число minor page faults.

**Что нельзя делать**: чередовать холодный и тёплый режим между запусками
одной конфигурации без явного указания этого как отдельного фактора — тогда
дисперсия результата будет объясняться состоянием кэша, а не паттерном
доступа, который вы якобы изучаете.

## 6. Размер файла относительно RAM

Если методология — холодный кэш, размер файла не обязан быть больше RAM
(кэш всё равно сбрасывается каждый раз), но должен быть достаточно большим,
чтобы время выполнения не тонуло в шуме (доли миллисекунды сложно измерить
стабильно). Ориентир — секунды выполнения на запуск.

Если методология — тёплый кэш и вы **хотите** сохранить видимую разницу
между `seq`/`rand` на уровне диска (а не только memcpy из RAM), файл должен
быть заметно **больше** объёма свободной RAM, чтобы часть данных не
поместилась в page cache целиком.

## 7. Продвинутая изоляция (опционально)

Для более строгого эксперимента, если хочется пойти дальше базового набора:

- `isolcpus=<N>` в параметрах загрузки ядра — полностью убирает ядро N из
  общего планировщика ОС, на него можно закрепить только ваш процесс.
- cgroups v2 (`cpuset`, `cpu.max`) — ограничение и изоляция ресурсов без
  перезагрузки системы.
- Отключение SMT/Hyper-Threading, если соседний логический CPU того же
  физического ядра может создавать интерференцию (`lscpu -e` покажет
  соответствие logical CPU → physical core).

Эти пункты не обязательны для сдачи базового варианта задания, но
пригодятся, если хотите объяснить остаточный разброс после базовой
настройки.

## 8. Чек-лист перед стартом серии измерений

- [ ] Фоновые процессы закрыты, `uptime`/`top` подтверждают простой
- [ ] Governor CPU зафиксирован (`performance`)
- [ ] Решение по Turbo Boost принято и задокументировано
- [ ] Процесс закрепляется на конкретном ядре (`taskset`)
- [ ] Приоритет процесса задан (если используется `nice`/`renice`)
- [ ] Методология кэша выбрана и одинакова для всей серии одной конфигурации
- [ ] Размер файла обоснован относительно объёма RAM и выбранной методологии
- [ ] «Снимок» состояния системы сохранён до и после серии измерений
