# Настройка и изоляция окружения эксперимента

> Общая методичка курса «Операционные системы». Применима к любому заданию,
> где вы измеряете время выполнения программы, поведение планировщика,
> потребление ресурсов или иные показатели ОС — вне зависимости от того,
> CPU-bound это эксперимент, IO-bound или память.

## 1. Зачем вообще контролировать окружение

Любое измерение времени/ресурсов в реальной ОС подвержено шуму, не
относящемуся к тому эффекту, который вы изучаете: фоновые процессы,
изменение частоты CPU, миграции между ядрами, состояние кэшей (CPU, файлового
кэша, TLB). Задача этого документа — дать чек-лист приёмов, которые убирают
или делают управляемым каждый из этих источников. Не все пункты нужны для
любого эксперимента — выбирайте применимые к вашей задаче и явно
фиксируйте выбор в отчёте.

## 2. Фоновые процессы

Закройте лишнее перед серией измерений: браузеры, IDE, синхронизации
облачных папок, индексаторы (`mlocate`/`plocate`, `tracker`), обновления
пакетов.

```bash
uptime                 # load average должен быть близок к 0 на простаивающей машине
top -bn1 | head -20     # %CPU процессов, фоновая загрузка по ядрам
```

Если стенд — виртуальная машина в облаке, вы не контролируете «соседей» по
физическому хосту. Для учебных целей это допустимо, но результат нужно
интерпретировать с этой оговоркой; для «чистого» эксперимента предпочтителен
bare-metal или выделенная ВМ с закреплёнными vCPU.

## 3. Частота CPU (DVFS) и Turbo Boost

Современные CPU меняют частоту на лету в зависимости от нагрузки и
температуры — прямой источник нестабильности между запусками, особенно
критичный для CPU-bound экспериментов.

```bash
cpupower frequency-info                      # текущий governor и диапазон частот
sudo cpupower frequency-set -g performance   # зафиксировать максимальную частоту
```

Governor'ы (`man cpupower`): `performance` (фиксированный максимум —
рекомендуется для экспериментов), `powersave`, `ondemand`/`schedutil`
(динамические — источник шума).

Turbo Boost (Intel) / Precision Boost (AMD) — опционально:

```bash
cat /sys/devices/system/cpu/intel_pstate/no_turbo    # 0 = turbo включён
echo 1 | sudo tee /sys/devices/system/cpu/intel_pstate/no_turbo   # выключить
```

Если недоступно на вашем железе/правах — явно укажите в отчёте, что Turbo
Boost не контролировался, и учтите это при интерпретации разброса.

## 4. Закрепление процесса на CPU (`taskset`)

Без явного закрепления планировщик может переносить процесс между ядрами
(`cpu-migrations` в `perf stat`) — разные ядра означают разное состояние
L1/L2 кэша и, возможно, разную текущую частоту.

```bash
taskset -c 2 ./your_program ...      # закрепить новый процесс на ядро 2
taskset -cp 2 <pid>                  # закрепить уже запущенный процесс
```

Перед выбором ядра посмотрите `mpstat -P ALL 1`, чтобы не выбрать ядро,
принимающее много прерываний (часто это CPU0).

Для экспериментов, где важно взаимодействие нескольких потоков/процессов
(например, задания про синхронизацию или планировщик), закрепление на разные
конкретные ядра — тоже часть постановки эксперимента, а не только защита от
шума: важно осознанно решить, что вы хотите изучить — поведение на одном
ядре, на разных ядрах одного сокета, или на разных сокетах (NUMA).

## 5. Приоритет планировщика (`nice`/`renice`)

Влияет на то, как охотно планировщик уступает CPU процессу при конкуренции.

```bash
sudo nice -n -5 taskset -c 2 ./your_program ...   # отрицательный nice → выше приоритет, нужен root
renice -n -5 -p <pid>                             # изменить приоритет уже запущенного процесса
```

Диапазон: от `-20` (наивысший приоритет) до `19` (наинизший); отрицательные
значения — только с правами root. Полезно как дополнительная защита от
вытеснения процесса другими задачами на стенде.

## 6. Состояние кэшей — если эксперимент касается памяти/диска

Если ваша программа читает файл или работает с большим объёмом данных,
состояние кэшей (файлового page cache, CPU-кэшей, TLB) может радикально
поменять результат — и это сильнее всего влияет на то, что именно вы
измеряете. Примите решение осознанно и одинаково для всей серии одной
конфигурации.

**Холодный кэш**: перед каждым запуском гарантированно убрать данные из
page cache:

```bash
sync
echo 3 | sudo tee /proc/sys/vm/drop_caches
```

(`1` — только pagecache, `2` — dentries/inodes, `3` — всё).

Такой режим измеряет «настоящую» стоимость обращения к диску/памяти —
разница между более и менее локальными паттернами доступа будет наиболее
выраженной.

Некоторые учебные программы сами предоставляют флаг для управления кэшем
(например, `--no-cache`), реализованный через `O_DIRECT`, `posix_fadvise`
или платформенно-специфичный API — если такой флаг есть, предпочитайте его
ручному `drop_caches`: это переносимо между Linux/macOS и не требует root.
Проверьте `--help`/исходный код конкретной программы, что именно делает
такой флаг, прежде чем полагаться на него в выводах.

**Тёплый кэш**: кэш прогревается один раз и далее не трогается всю серию —
измеряет эффективность доступа к уже закэшированным данным.

**Что нельзя делать**: чередовать холодный и тёплый режим между запусками
одной конфигурации без явного указания этого как отдельного фактора —
тогда разброс объясняется состоянием кэша, а не тем эффектом, который вы
изучаете.

## 7. Размер рабочего набора данных относительно RAM/кэшей

Если методология — холодный кэш, размер обрабатываемых данных не обязан
превышать RAM, но должен быть достаточно большим, чтобы время выполнения не
тонуло в шуме (секунды, а не микросекунды на запуск — ориентируйтесь по
своей программе).

Если методология — тёплый кэш и вы хотите сохранить видимую разницу на
уровне диска/памяти (а не только скорость копирования из уже прогретого
кэша), рабочий набор должен быть заметно **больше** объёма кэша
соответствующего уровня (page cache, LLC CPU и т.д.).

## 8. Продвинутая изоляция (опционально)

Для более строгого эксперимента:

- `isolcpus=<N>` в параметрах загрузки ядра — полностью убирает ядро N из
  общего планировщика ОС.
- cgroups v2 (`cpuset`, `cpu.max`, `memory.max`) — ограничение и изоляция
  ресурсов без перезагрузки.
- Отключение SMT/Hyper-Threading, если соседний логический CPU того же
  физического ядра может создавать интерференцию (`lscpu -e` покажет
  соответствие logical CPU → physical core).
- Учёт NUMA-топологии (`numactl --hardware`, `numactl --cpunodebind=0
  --membind=0 ./your_program`) — важно для экспериментов, где задействованы
  и CPU, и память на многосокетных машинах.

Эти пункты не обязательны для базовых заданий, но пригодятся, если хотите
объяснить остаточный разброс после базовой настройки, либо задание прямо
требует изучения NUMA/изоляции ядер.

## 9. Чек-лист перед стартом серии измерений

- [ ] Фоновые процессы закрыты, `uptime`/`top` подтверждают простой
- [ ] Governor CPU зафиксирован (`performance`), если частота важна для эксперимента
- [ ] Решение по Turbo Boost принято и задокументировано
- [ ] Процесс закрепляется на конкретном ядре (`taskset`), если это релевантно
- [ ] Приоритет процесса задан, если используется `nice`/`renice`
- [ ] Методология состояния кэша выбрана и одинакова для всей серии (если применимо)
- [ ] Размер рабочего набора данных обоснован относительно объёма RAM/кэшей (если применимо)
- [ ] «Снимок» состояния системы сохранён до и после серии измерений
