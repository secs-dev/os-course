## Сборка и запуск

Из каталога `lab/vtsh`:

```sh
cmake -S . -B build
cmake --build build
./build/bin/vtsh
```

Собственный набор Python-тестов использует этот же путь к исполняемому файлу:

```sh
python3 -m unittest discover -s test
```

## 1. Цель работы

В этой лабораторной работе необходимо разработать **простую командную оболочку**.

Оболочка должна показать, как пользовательская программа запускает другие
программы с помощью системных вызовов ОС, передаёт им аргументы и окружение,
ожидает их завершения и управляет фоновыми процессами.

Задача не состоит в повторении Bash. Не требуется поддерживать весь синтаксис
POSIX Shell. Главное — понять:

- зачем операционной системе нужна командная оболочка;
- как создаются и завершаются процессы;
- чем отличаются родительский и дочерний процессы;
- как передаются аргументы и переменные окружения;
- как оболочка получает код завершения программы;
- как реализуются последовательное, условное и фоновое выполнение;
- как устроены сигналы, группы процессов и каналы (`pipe`).

В руководстве намеренно нет готовой реализации. Названия системных вызовов,
этапы алгоритмов, примеры ввода и вопросы для проверки должны помочь спроектировать
решение самостоятельно.

## 2. Состав задания

### 2. Функциональность VTSH

Оболочка должна:

1. быть написана на C (или другой низкоуровневый язык с возможностью выполнения
   системных вызовов напрямую через C-API);
2. показывать приглашение к вводу;
3. запускать внешнюю программу по абсолютному пути;
4. поддерживать команды `cd` и `exit`;
5. передавать новой программе аргументы и текущее окружение оболочки;
6. корректно ожидать завершения запущенных подпроцессов и получать их статус;

Дополнительные функции (по варианту):

1. поддерживать конвейеры с помощью `|`;
2. запускать простую команду в фоновом режиме с помощью `&`;
3. поддерживать логические операторы в соответствии с вариантом;
4. ограничивать ресурсы запускаемых программ в соответствии с вариантом.

## 3. Минимальный синтаксис

Для базовой версии достаточно следующей модели:

- команда — имя программы и ноль или больше аргументов;
- слова разделяются одним или несколькими пробельными символами;
- операторы `;`, `&&`, `||`, `&`, `|` отделяются пробелами;
- `&` применяется только к одинарной простой команде (без операторов);
- некорректная или неполная конструкция должна выдавать понятную ошибку, а не
  приводить к аварийному завершению оболочки.

Примеры допустимого ввода:

```text
/bin/echo hello world
printf one ; printf two
false && echo not-run
false || echo fallback
sleep 2 &
```

Можно дополнительно расширить возможности синтаксиса. Ограничения синтаксиса
должны быть описаны в отчёте и проверены тестами.


## 4. Рекомендуемая архитектура

Программу можно разделить на четыре логические части:

1. **REPL** — приглашение, чтение строк и завершение оболочки;
2. **parser** — преобразование строки в команды, аргументы и операторы;
3. **executor** — запуск команд и применение правил логических операторов;
4. **process manager** — ожидание, хранение фоновых задач и сбор завершившихся
   процессов.

Необязательно помещать каждую часть в отдельный файл, но их обязанности не
следует смешивать. Например, parser не должен создавать процессы, а обработчик
сигнала не должен разбирать новую командную строку.

Полезно заранее определить две внутренние сущности:

- **простая команда**: массив аргументов, где первый элемент — имя программы;
- **план выполнения**: список команд и операторов между ними.

Для фоновых задач дополнительно понадобятся идентификатор задачи, PID или PGID,
исходный текст команды и атрибут текущего состояния.

## 5. Пошаговая инструкция к разработке

### Шаг 1. Реализуйте цикл оболочки

На каждой итерации:

1. при интерактивном запуске покажите приглашение;
2. прочитайте одну строку целиком;
3. удалите завершающий перевод строки;
4. пропустите пустую строку;
5. передайте строку parser;
6. выполните полученный план;
7. перед следующим приглашением проверьте завершившиеся фоновые процессы.

Приглашение лучше выводить только тогда, когда стандартный ввод связан с
терминалом. Это упрощает автоматическое тестирование через перенаправление
ввода.

Сочетание клавиш `Ctrl-D` не посылает сигнал. Терминал сообщает программе конец
файла (EOF), если во входном буфере нет данных. В этом случае оболочка должна
аккуратно завершить цикл, освободить память и решить, что делать с ещё
работающими фоновыми задачами. Выбранная политика должна быть описана в отчёте.

### Шаг 2. Разберите простую команду

Сначала поддержите только имя программы и аргументы. Проверьте случаи:

- пустая строка;
- пробелы в начале и конце;
- несколько пробелов между словами;
- команда без аргументов;
- большое число аргументов;
- слишком длинная строка.

Массив аргументов для запускаемой программы должен завершаться специальным
нулевым элементом. Решите, кто владеет выделенной памятью и в какой момент она
освобождается.

Не начинайте с кавычек и подстановок. Сначала добейтесь надёжного запуска простой
команды.

### Шаг 3. Запустите одну программу

Общий сценарий запуска выглядит так:

1. родитель создаёт дочерний процесс способом, соответствующим варианту (`fork`/...);
2. дочерний процесс подготавливает своё состояние и заменяет свой образ внешней
   программой через вызов системной функции из семейства `exec`;
3. при ошибке `exec` дочерний процесс печатает диагностическое сообщение и
   немедленно завершается;
4. родитель сохраняет PID и ожидает завершения дочернего процесса с помощью
   функции `wait`, если команда не выполняется в фоновом режиме;
5. родитель преобразует результат функции ожидания в код выполнения команды.

Запрещено вызывать внешнюю программу через `system`, `popen` или запуск `/bin/sh -c`
— задача состоит в самостоятельной разработке shell, а не в использовании готового.

Рекомендуемые соглашения об ошибках:

- программа не найдена — статус `127`;
- программа найдена, но не может быть запущена — статус `126`;
- ошибка создания процесса остаётся ошибкой текущей команды, но не превращается
  в ошибку shell как приложения, то есть его работа не завершается и shell
  продолжает принимать новые команды.

Перед реализацией изучите соответствующие страницы `man`:

- [`fork(2)`](https://man7.org/linux/man-pages/man2/fork.2.html),
  [`vfork(2)`](https://man7.org/linux/man-pages/man2/vfork.2.html),
  [`clone(2)`](https://man7.org/linux/man-pages/man2/clone.2.html);
- [`exec(3)`](https://man7.org/linux/man-pages/man3/exec.3.html) и
  [`execve(2)`](https://man7.org/linux/man-pages/man2/execve.2.html);
- [`wait(2)` / `waitpid(2)`](https://man7.org/linux/man-pages/man2/wait.2.html);
- [`_exit(2)`](https://man7.org/linux/man-pages/man2/_exit.2.html).

### Шаг 4. Пробросьте окружение

Новая программа должна получить переменные окружения shell. Проверьте это с
помощью утилит `env` или `printenv`.

### Шаг 5. Корректно обработайте завершение процесса

Ожидание подпроцесса может завершиться по разным причинам. Обработайте статус с
помощью предназначенных для этого макросов и различайте:

- обычное завершение;
- завершение по сигналу;
- остановку или продолжение процесса, если эти состояния отслеживаются.

Ожидание может быть прервано сигналом, например `SIGINT`. В этом случае
системный вызов может вернуть ошибку `EINTR`; если сигнал не должен завершать
операцию ожидания, его нужно обработать и повторить ожидание.

Для процесса, завершённого сигналом, удобно сформировать внутренний ненулевой
статус по правилу `128 + номер сигнала`. Главное — использовать одно соглашение
во всём executor.

## 6. Расширения

### 6.1. Конвейеры

Конвейер связывает стандартный вывод одной программы со стандартным вводом
следующей:

```text
printf hello | wc -c
```

Для каждого соседнего звена нужен канал, созданный через `pipe`. После создания
ребёнка нужные концы подключаются к `STDIN_FILENO` и `STDOUT_FILENO` через
`dup2`. Все неиспользуемые файловые дескрипторы закрываются и в детях, и в
родителе.

Типичная причина зависания — открытый в родителе дескриптор записи: последний
читатель не получает EOF. Сначала реализуйте конвейер из двух программ, затем
обобщите его на произвольное число звеньев. Родитель должен дождаться всех
процессов foreground-конвейера; статусом конвейера обычно считают статус его
последнего звена.

Подумайте, как с помощью конвейеров теперь можно сделать перенаправление потока
в файл (`cat kek.txt lol.txt > idk.txt`). Проверьте своё решение.

### 6.2. Фоновое выполнение

Для команды с `&` родитель не должен выполнять блокирующее ожидание. Он
сохраняет информацию о задаче и сразу показывает следующее приглашение к вводу.

Однако завершившийся в фоне подпроцесс всё равно должен быть обработан.
Периодически вызывайте **неблокирующее** ожидание:

- перед показом приглашения к вводу;
- после обработки строки;
- при получении сигнала `SIGCHLD`, если реализовано расширенное управление
  сигналами.

> [!NOTE]
> Обработчик `SIGCHLD` должен делать минимум работы. Сложное обновление структур
> и печать лучше выполнять в основном цикле.
>
> Помните, что один сигнал может соответствовать завершению нескольких
> процессов, поэтому проверка должна продолжаться, пока доступен хотя бы один
> изменивший состояние дочерний процесс.

### 6.3. Логические операторы

Сначала parser должен отделить команды от операторов и обнаружить синтаксические
ошибки.

Executor хранит статус последней действительно выполненной команды и решает,
нужно ли запускать следующую:

- после `;` — всегда;
- после `&&` — только после успеха;
- после `||` — только после ошибки.

Порядок выполнения команд ленивый: если первый операнд даёт понять, какой будет
итоговый результат, то второй операнд вычислять не требуется, то есть вторая команда
не выполняется и не создаёт процесс, не меняет статус последней выполненной
команды.

| Оператор | Поведение |
|---|---|
| `cmd1 ; cmd2` | выполнить `cmd1`, затем выполнить `cmd2` независимо от статуса `cmd1` |
| `cmd1 && cmd2` | выполнить `cmd2`, только если `cmd1` завершилась успешно |
| `cmd1 \|\| cmd2` | выполнить `cmd2`, только если `cmd1` завершилась с ошибкой |

Успехом считается код завершения `0`. Любой ненулевой код или завершение по сигналу считается ошибкой.

Проверьте не только пары, но и цепочки, например:

```text
true && echo recovered && false
false ; echo no ; echo yes
false || false || echo recovered
```

### 6.4. Вспомогательные ограничения ресурсов

Реализуйте **ограничение ресурсов запускаемых программ** по варианту расширения,
назначенному преподавателем:

| Вариант | Ограничение | Идея проверки |
|---|---|---|
| 1 | `RLIMIT_NPROC` — число процессов и потоков пользователя | ограниченное число попыток создания потомков, проверка отказа |
| 2 | `RLIMIT_NOFILE` — файловые дескрипторы | открытие файлов/сокетов до отказа с удержанием дескрипторов |
| 3 | `RLIMIT_FSIZE` — размер отдельного файла | запись сверх лимита, проверка размера файла и статуса |
| 4 | `RLIMIT_STACK` — размер стека | контролируемая глубокая рекурсия с фактическим расходом стека |
| 5 | `RLIMIT_AS` — виртуальное адресное пространство | последовательное выделение и удержание памяти до отказа |

Используйте `getrlimit()` / `setrlimit()`; значение лимита должно быть
настраиваемым. Ограничение должно действовать на запускаемую программу и
наследоваться её потомками, не меняя без необходимости лимиты самого shell.
Документация: `man 2 getrlimit` / `man 2 setrlimit`.

Для тестирования запускайте небольшую вспомогательную программу сначала с
достаточным, затем с уменьшенным лимитом. Проверяйте реальный отказ операции
или завершение по сигналу, а не только успех `setrlimit()`, и убедитесь, что
shell продолжает работу. Настоящую fork bomb запускать не стоит.

Особенности Linux, безопасная установка лимитов и подробности проверок приведены
в [приложении A](#приложение-a-ограничения-ресурсов-в-linux).


## 7. Собственные тесты на Python

Тесты являются частью работы, а не только способом выставления оценки. Создайте
отдельный набор тестов, который запускает собранный shell как дочерний процесс,
передаёт команды через `stdin` и читает `stdout` и `stderr`.

Рекомендуется использовать стандартные модули `subprocess`, `unittest` или
`pytest`. Не запускайте проверяемые команды через `shell=True`, т.к. вам нужно
протестировать свой vtsh, а не системную оболочку.

Минимальный набор сценариев (с учетом вариантов):

1. пустая строка и EOF;
2. вызов программы по абсолютному пути;
3. программа без аргументов и с несколькими аргументами;
4. лишние пробелы;
5. передача специально заданной переменной окружения;
6. несуществующая и неисполняемая команда;
7. ошибочный синтаксис не завершает shell;
8. коды завершения `0` и не `0`;
9. каждая ветвь логических операторов (`;`, `&&`, `||`);
10. цепочка из трёх и более команд;
11. фоновая команда не блокирует следующую;
12. после фоновой команды не остаётся zombie;
13. конвейер передаёт данные и получает EOF;
14. после выполнения `cd` новые команды выполняются в контексте указанной
    директории;
15. ограничения на ресурсы работают.

## Приложение A. Ограничения ресурсов в Linux

### Установка ограничений и их наследование

Ограничение (лимит) обычно устанавливают после `fork` в дочернем процессе до
`exec`. Лимиты наследуются при создании потомков и сохраняются после `exec`, но
обычно учитывают ресурсы каждого процесса отдельно, а не сумму по дереву
потомков. У `RLIMIT_NPROC` особая область учёта — реальный пользователь.

Есть два параметра ограничений: **soft** и **hard limit** — уточните, в чем
разница и в каком случае следует какие устанавливать. При установке нового
значения учитывайте исходные значения, полученные с помощью `getrlimit()`.

Проверяйте ошибки установки лимита. Shell должен продолжить принимать
команды и не запускать программу без заданного ограничения.

> [!WARNING]
> После `vfork()` нельзя произвольно вызывать функции, в том числе `setrlimit()`,
> до `exec()` или `_exit()`. Для такого варианта потребуется отдельная программа-
> обёртка, запускаемая через `exec`: она установит лимит и выполнит целевую
> программу. Для `clone()` учитывайте выбранные флаги совместного использования
> памяти и ресурсов; не переносите схему для `fork()` без проверки документации.

Текущие лимиты можно проверить через `/proc/<pid>/limits` (`man 5 proc_pid_limits`),
а для экспериментов вне shell использовать `prlimit` (`man 1
prlimit`).

Дополнительные материалы:

- [`getrlimit(2)` / `setrlimit(2)`](https://man7.org/linux/man-pages/man2/getrlimit.2.html)
  — семантика лимитов, наследование и ошибки;
- Michael Kerrisk, *The Linux Programming Interface*, глава **Process Resources**;
- [cgroup v2 PIDs controller](https://docs.kernel.org/admin-guide/cgroup-v2.html#pid)
  — `pids.max` ограничивает число задач в cgroup и её дочерних cgroup, в отличие
  от учёта по real UID в `RLIMIT_NPROC`.
